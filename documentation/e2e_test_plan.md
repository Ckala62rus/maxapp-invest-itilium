# План E2E / интеграционных проверок (тестовая среда)

## Зачем

Проверять «разом» сценарии мини‑приложения против **реального** ITILIUM на **тестовом** контуре: списки заявок, карточка, смена статуса, смена ответственного, комментарии, согласование — без ручного клика по чек-листу при каждом релизе.

## Варианты стека (от практичного к полному)

### 1. **Playwright** (рекомендация по умолчанию)

- **Плюсы:** стабилен к асинхронной подгрузке, хорошие отчёты, trace/video, TypeScript, один движок и для UI, и для `request` к API.
- **Как с MAX:** mini app в iframe/отдельном origin — часто удобнее **гибрид**:
  - **API E2E:** прямые `POST/GET` на ваш backend (`/api/v1/...`) с **заранее снятой** парой `Authorization: Bearer` + сценарий тестового пользователя (или короткоживущий токен из шага pre-test).
  - **UI E2E:** открытие Vite/стенда, при необходимости подмена `initData` через `page.addInitScript` / query для **headless** проверок без реального бота.
- **Где крутить:** CI (по расписанию или вручную) с секретами в GitHub Actions / внутреннем runner; `baseURL` и ITILIUM — только test.

### 2. **Cypress**

- **Плюсы:** удобный DX для SPA, time travel.
- **Минусы:** вторая лицензия/модель для параллели в CI, с сетевыми вызовами к внешнему ITILIUM чаще тяжелее, чем Playwright.

### 3. **Только API: Postman / Bruno + Newman / k6 сценарии**

- **Плюсы:** быстро покрыть backend‑контракты, смена ответственного, комментарий, confirm — **без браузера**.
- **Минусы:** нет проверки реального клика по UI и кэша фронта.

**Практичная связка:** **Newman/скрипты на API** (смоук после деплоя) + **сузить** Playwright до 3–5 критичных UI‑сценариев.

## Минимальный набор сценариев на тестовом контуре

1. **Идентичность / профиль** — `auth`, `GET /api/v1/users/me` (или цепочка MAX validate, если тест с реальным initData).
2. **Мои заявки** — `GET /api/v1/tickets` (и при сбое `list_sc` — fallback по номерам).
3. **В ответственности** — `GET /api/v1/tickets/responsible`.
4. **Карточка** — `GET /api/v1/tickets/{number}`.
5. **Комментарий** — `POST /api/v1/tickets/{number}/comments` (и что тело доходит в 1С).
6. **Статус** — смена через предусмотренный endpoint, если в UI доступно.
7. **Смена ответственного** — загрузка `responsibles` + `POST` смены + повтор `GET` карточки.
8. **Согласование (confirm)** — если используется в тесте, отдельный сценарий с тестовой заявкой.

Порядок важен там, где заявка «одноразовая»; для стабильности завести **учётки и номера тестовых заявок** в конфиге среды (не в репозитории).

## Секреты и среда

- Токены, `MAX_BOT`, пароли к ITILIUM — только **CI secrets** / внутренняя песочница.
- В репозитории — пример `*.example.env`, без реальных URL с учётками.
- Тестовая база 1С должна **разрешать** массовые сценарии (одна заявка на смену ответственного, отдельные — только на чтение).
